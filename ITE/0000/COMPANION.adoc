= Companion to ITE-0000: reasoning, alternatives, tooling and open questions

This document carries the material the ITE points at rather than states: the tooling the proposal asks
the project to publish, the portability of the criterion across envelope families,
the reasoning in full, every alternative considered and why each was rejected, and
what remains open.

Nothing here is normative. Where this document and the ITE differ, the ITE is the
proposal.

== The index: a registry of predicate types

The directory publishes a machine-readable index, one record per type, served from
a stable URL through the redirect infrastructure the project already runs, so a
tool resolving a `predicateType` has something to resolve against. Each record
carries the short name; the `predicateType` URI; the location of the specification,
which is a repository path for a hosted type and a URL for an observed one; the tier, for
hosted types; a status of `active`, `deprecated`, `withdrawn` or `observed`; the
ITE-10 class, `informational` or `transformational`; a change controller; a
normative reference, being the document a verifier is expected to implement; the
redirect status of the URI; and the date first published. Where an evidence bundle
exists, the record also carries the corpus digest at the corpus revision the evidence was
produced against and a link to the implementation report. The generator reconciles
the index against `layouts/index.redirects` in `in-toto/in-toto.io` and reports
divergence, so the index is authoritative and any divergence between the two is reported.

Four fields do work worth naming.

Status is the security control. A directory that can only add entries has no
response available when a hosted type turns out to be superseded or harmful. That is
the concrete form of the meeting's worry that a free-for-all repository would
surface "this project used in-toto but still got affected" type of issues.

Class answers a request already open on the in-toto/attestation issue tracker. Issue 377, "Should we
categorize different predicate types?", open since 2024-08-14 with no comments,
asks for this axis: "My recommendation is to do a survey of the existing vetted
predicate types that we have, and separate them at two levels: the ITE-10 classes
and further subdivide informational predicates into a few more categories." This
ITE takes the first level and names the second as a follow-on in <<unresolved>>.

Change controller answers who may revise or retire a listed type whose author
has moved on, which the demotion path otherwise leaves to nobody. Standard
registry practice, one field.

`observed` records make this the registry of predicate types, not only of hosted
ones. The meeting asked for that, in the words "Puerco: Would be nice to have a
registry of types for people like myself", and recorded that survey data already exists:
"Related to Sivana's work \"here are the types we've seen in the wild that people
have defined and are using\"" and "Sivana: there's a lot of data!". An `observed`
record carries a URI, a first-observed reference and a change controller where
known, and asserts nothing beyond having been seen. Two things populate it: the
harvester in <<tooling>>, and an invitation to the survey's author to contribute
theirs on whatever terms they prefer. These records are also the evidence base the
adoption door needs and would otherwise lack.

== Promotion, demotion, contest, and deprecation

These are stated normatively in the ITE itself and are not restated here. Two notes
on why they read as they do.

The objection period carries a default, fourteen days or one community meeting
cycle, because "a stated objection period" with no value reintroduces the unbounded
reading task this proposal removes. A message in `#in-toto-attestations` on
2026-07-13 proposed a regular `/attestation` sync to review pending predicate pull
requests; if it happens it is the natural home for promotion review.

Promotion requests going stale after a month is the timeline ITE-1 already applies
to ITEs themselves: "a draft without activity for a month since the last comment is
expected to be moved to deferred status", with two months as the ceiling on any
other state. contrib entries do not expire, because a hosting tier with an expiry
is a queue, and contrib is not one.

== Tooling the project publishes

The criterion claims a submitter can check themselves before opening a pull
request, which is only true if there is something to check against. Six small
artifacts, all part of this proposal and offered in link:README.adoc#prototype-implementation[the ITE's prototype section]:

. A submission checker. Verifies the ITE-9 sections are present, against
  `spec/predicates/template/template.md`, which keeps the check correct when the
  template moves; that the schema parses, that a corpus is present and every
  vector labelled, that every `MUST-REJECT` vector cites a section and a layer,
  that every `INDETERMINATE` vector states its readings, that the index record is
  well-formed, and that the bundle verifies. This is the preflight that turns
  review from a verdict delivered after a wait into a checklist completed before
  the pull request opens.
. A schema-driven reference validator, built on the pseudocode already in
  `docs/validation.md` and the existing `rust/src/validator.rs`. It gives every
  corpus a target that does not depend on generated bindings, which is what makes
  E1 reachable for a type with no protobuf definition.
. A corpus runner as a make target, beside `make go_test`, `make py_test` and
  `make cargo_test`. Conformance is then native infrastructure.
. A vector generator and coverage report, emitting the required-field,
  constrained-value and declared-parsing-rule vectors mechanically from the schema
  so E1's coverage obligation is a number.
. An implementation report, generated in CI: corpus vectors by implementation
  by outcome, published with the specification. This is the shape W3C's
  Recommendation track uses for the same purpose, and one page across all types,
  where a private table per type is the usual arrangement, makes conformance a
  standing visible property of the directory, as Web Platform Tests does.
. An observation harvester, enumerating `predicateType` values in public
  attestations and proposing `observed` index records, so the registry half of the
  index is populated by a job.

== Portability across envelope families

A predicate type is a schema plus its semantics. Neither the criterion nor the
index depends on the envelope, signature format or serialization carrying it: a
bundle establishing that two parties reach the same decisions on a corpus
establishes it for the predicate as carried anywhere, including in neighbouring
receipt and envelope families such as IETF SCITT and COSE receipts. Two listed
types are BOM formats defined by other communities and served from their domains,
so the directory already spans more than one family in practice. Saying this once
makes this index the thing such a family resolves against, and no second registry
is created. The conformance mechanics of carrying in-toto predicate types in another
family are a follow-on named in <<unresolved>>.

== Non-goals

This ITE does not gate publication, does not detect generated content, does not
assess whether a predicate type is worth having, does not re-evaluate existing
vetted predicates, does not change the ITE-9 document format, and does not change
namespace or redirect policy.

== Evidence of consensus, and the concerns raised

This ITE originates in a single recorded discussion, and its evidence of consensus
is that discussion alone. From the notes of 2026-08-07, under
`in-toto/attestation reviews`: "Aditya: Vetted could be for fundamental SDLC types
that lend themselves to reuse"; "Aditya: We could have two tiers -- vetted and
community or contrib"; "Aditya: I'm coming around on the two tier system";
"Aditya: yes, we'd follow governance for /attestation and in-toto as a whole,
probably a process ITE to set this up"; "No objections to file a process ITE".

The concerns recorded in the same discussion, which this ITE must address rather
than restate: that a free-for-all repository would produce
"misunderstandings/poorly defined types surfacing \"this project used in-toto but
still got affected\" type of issues", answered by the criterion, by `deprecated`
and `withdrawn`, and by the adjacent statement on both listings; that the
maintainers may not have the expertise for what gets submitted, answered by
choosing evidence a non-expert can check; that generated predicates arrive in
volume, a participant reporting having "seen a lot of AI generated predicates",
answered honestly below; and "Sivana: Do we need approvals from maintainers?",
answered in the promotion process by following existing governance.

Nothing in that meeting endorsed this document, which did not exist at the time.
It is offered as one way to do what the meeting agreed should be done.

== Why evidence rather than a quality judgement

A quality judgement does not survive volume, does not transfer between reviewers,
and cannot be contested on its own terms. "We can tell" is true of a maintainer
reading their third submission and not their thirtieth, and it gives a rejected
submitter nothing to act on. Evidence has a property a judgement does not: the
submitter can run it before submitting, which removes most of the round-trips that
make the queue slow. The shape is not novel. The Kubernetes conformance
programme has run it at scale for a decade, with a vendor running a published
suite and submitting results as a pull request to a public repository where a
machine-checked list confirms the submission is well-formed before a human looks
at it. That is this proposal's promotion mechanism and its submission checker,
proven elsewhere.

== Why an implementation by someone other than the author

Single-implementation specifications are the standard failure mode in standards
work, and independent implementation experience is asked for elsewhere before a
specification advances. The W3C Process, when assessing
implementation experience, asks "are there independent interoperable
implementations of the current specification?" and, as a separate item, "are there
implementations created by people other than the authors of the specification?"
The second is E2 almost verbatim.
RFC 2026 conditions advancement to Draft Standard on "at least two independent and
interoperable implementations from different code bases". ITE-1 says the same in
this project's own voice: "the principle of \"rough consensus and running code\"
is still useful when it comes to resolving many discussions of API details."

The mechanism is not that a second implementation finds bugs. It is that a second
implementer cannot read the author's intent off the page, and the places where
the text relied on that intent are where the two readings part. That is also why E2 asks what tooling
each implementation used: two readings produced by the same tool from the same
text are one reading counted twice.

== Why negative controls, and why blind

An example-only corpus tests the author's ability to produce a valid document; the
interesting content of a specification is what it refuses. A run by an implementer
who helped shape the corpus tests their understanding of the corpus. Only a
first run against unseen material tests the text. Blindness is required once only, because maintaining it is genuinely costly and the
information is concentrated in the first run. What E3 requires throughout is
honest labelling, which is free: once the authors have named a fix or a vector to
the implementer the next run is `directed`, and a bundle whose later runs are all
labelled `directed` is labelling its runs accurately.

== What the criterion costs a submitter

A criterion only its proposers can meet is a bad criterion. To publish, nothing
changes: write the specification in the ITE-9 format, open the pull request, be
listed in contrib.

To reach vetted, three artifacts are added. The corpus: ITE-9 already requires
an example, so the accepting half largely exists; the new work is the rejecting
half and the section citations, hours for a small schema, and it is the part most
useful to the author, because writing a `MUST-REJECT` vector is how an author
discovers which fields they never actually constrained. *The results and defect
record*: files, plus a label per run. *The second implementer, or the independent
corpus author*: the expensive item, and the only one. It is expensive because it
needs a second person, and the project can lower that cost far more cheaply than
any individual submitter:

* **Any second person counts**: a colleague, a classmate, a co-maintainer, a
  student, someone who answers a label. There is no requirement of institutional
  independence, funding or a second organisation, and there deliberately MUST NOT
  be one: such a requirement would sort submissions by the size of the submitter's
  employer, which is not a property of a specification.
* **A matching mechanism.** The repository SHOULD carry a `seeking second
  implementer` label and the meeting a standing slot for it, if the maintainers
  want them, so "I have nobody" becomes a request the community can answer rather
  than a disqualification absorbed alone.
* **Pairing at contributor events.** Implementing someone else's draft
  specification from its text is bounded, needs no prior context and produces
  something the project wants. The project's own notes record ContribFest among
  its KubeCon plans, and this is a natural fit for a future cycle.
* **A standing offer.** The drafter will act as second implementer, or write
  negative controls, for any open predicate submission whose author wants one, on
  no conditions. That offer is open now and does not depend on this ITE.

== What this criterion excludes, and who it disadvantages

It does not judge whether a predicate is a good idea. The largest limitation,
and it must not be glossed. The criterion measures _determinacy_, meaning whether two
people reading a specification reach the same decisions; a well-specified bad idea
passes. A type that duplicates an existing one, models the supply chain
wrongly, or answers a policy question nobody asked will sail through a corpus and
two implementations. It replaces one of the two review questions, not both, so
link:README.adoc#specification[the ITE's Specification] proposes composing it with a subject-matter scope. The
other question is still a judgement, still needs the meeting, and is where
attention should go once it is no longer spent on determinacy.

Nor does it detect AI-generated submissions, and it does not try to. The meeting
asked whether, with LLMs, the original purpose of the vetted predicates is still
tenable. The purpose is tenable and the instrument is not: a model can produce a
conformance corpus as readily as a specification. What changes is the axis. Review
moves off prose quality, where generated text is strongest and a reviewer's
judgement least transferable, and onto whether two parties who did not coordinate
agreed. E2 accordingly requires the tooling behind each implementation to be
declared, since that is where correlation between two apparently independent
readings lives. The criterion is indifferent to authorship, the honest position
given authorship is not verifiable: a specification drafted with a model, with a
real corpus, a real second implementer and a real defect record, works.
Contribution provenance is a separate matter under discussion in
`in-toto/community` issue 53, which this ITE neither duplicates nor pre-empts.

There is a bias toward mechanically checkable semantics. A predicate carrying
structured machine-generated data has a large surface to conformance-test; one
carrying a human judgement (that a review was adequate, that a risk was accepted)
has a much smaller one, because the judgement is not checkable and only the
field discipline around it is. The bias is real and this design does not remove
it. The mitigations are computing coverage against schema surface, allowing `INDETERMINATE` so a specification is not forced to
invent precision, and reviewers being explicit that a judgement-carrying predicate
demonstrates determinacy of its envelope, not of its content.

The submitter with nobody to ask is disadvantaged. After the matching
mechanism and the other two doors, someone proposing a type for a system only
their employer operates may have no realistic second implementer, and cannot reach
vetted by effort. The honest answer is not to weaken the criterion for them but
that such a type is what contrib is for. The default landing tier is therefore
contrib, publication is not gated, contrib entries do not expire, and the
listing is a first-class part of the directory. If contrib
comes to read as failure, this criterion becomes a barrier and the ITE will have
done harm.

Reviewers pay something too. Someone must run the corpus. The claim is
not that review becomes free, but that the check moves from an unbounded reading
task requiring domain expertise to a bounded verification task CI performs and a
generalist can confirm.

== Alternatives considered

Maintainer judgement guided by a rubric:: Still a reading task, still needs
domain expertise, still does not transfer between reviewers. It formalises the
question the meeting could not answer.

Artifact-based replay instead of person-based independence:: The strongest
alternative: pin the specification at a commit, generate the vector matrix from
the schema, and grant vetted when two independently submitted signed bundles
agree, with no named second implementer. Three of its four mechanisms are better
than what this ITE first proposed and have been merged in: authorship defined at
a commit, coverage computed by tooling, and the bundle signed and digest-pinned. The fourth is not adopted: dropping the named second person makes
the criterion satisfiable only by parties who can run a project-supplied harness
twice, and loses the semantic disagreements that appear when a human reads a
sentence differently. Its honest cost, now inherited, is that the project must
build and maintain the generator and harness, and both are in <<tooling>> and in
the prototype.

Requiring an organisational sponsor or named adopter at submission:: Sorts
submissions by the submitter's employer and excludes individuals, students and
academics, a substantial part of this community. Retained only as the adoption
door, where it measures uptake of an existing type and does not act as a barrier to entry.

Filtering on disclosure of AI assistance. Not verifiable by the reviewer, and
aimed at contribution provenance rather than specification quality. Issue 53 is
the right home: it proposes org-level policy and leaves per-project limits to
sub-projects, which is the seam this ITE fits into, and duplicating it would
create two inconsistent policies on one repository.

Time in contrib alone. A reasonable second door and an unreasonable only door,
since it makes the tier a function of patience.

A prose style guide. The attestations style guide raised at the meeting borrows
a useful shape: graded levels, where an adopter implements the level it can
support rather than passing or failing one bar. This ITE borrows that shape, its
key-term discipline, and its principle of being transparent about limitations,
which is what <<who-this-disadvantages>> exists to satisfy. Its content addresses
how attestations are presented to package consumers in registry interfaces; the
string "predicate" does not appear on any of its five pages, so it does not
address whether a specification is determinate, which is what a tier boundary has
to answer.

A shared conformance harness only, with no tiers:: Attractive, and half of what
is proposed here, but a harness with nothing to sort on leaves the queue where it
is. The tiers give the evidence somewhere to land.

On the names. The meeting offered vetted and either `community` or contrib.
This ITE uses contrib; the name is not load-bearing and the project should use
whichever it prefers. One consideration: in Debian's archive layout contrib
already means packages depending on non-free ones, a faintly second-class sense
this ITE spends effort arguing against, and `community` carries no such freight.

[[unresolved]]

== Unresolved, and two follow-on documents

. Should the repository evolve to be a hosting location for predicates? Asked
  at the meeting, unanswered, upstream of everything here. This ITE argues that
  tiering makes hosting affordable, because the cost is unbounded only while every
  hosted type carries implied endorsement. That argument is recorded here and left open.
. Which existing types are vetted on adoption? This draft says all, by
  grandfathering; reclassifying any needs its own discussion and the affected
  authors' consent.
. Whether a subject-matter scope is adopted alongside the criterion, and what it
  is. This ITE proposes composition and takes no position on the scope, which is
  the maintainers' to draw.
. Who assigns tiers, and by what majority? Maintainers, following existing
  governance, with an announcement and a bounded objection period. RFC 8126's
  Designated Expert is the nearest existing mechanism if a named role is wanted.
. Does contrib accept types the maintainers consider poorly conceived? This
  draft says yes, absent duplication or harm, because a hosting tier with a
  quality filter is a vetted tier with extra steps. Reasonable people will
  disagree.
. May a contrib type hold a URI under `https://in-toto.io/attestation/`, and
  who decides the redirect list? Left unchanged and unanswered, because the
  drafter has a submission claiming such a URI and should not write the rule that
  governs it. The index records each type's redirect status so that whoever
  decides, the decision is recorded.
. Follow-on: the predicate taxonomy. Issue 377 asks for the ITE-10 classes
  and a further subdivision of informational predicates. This ITE takes the
  classes as an index field; the subdivision is a separate document, which the
  drafter intends to write with the issue's author if they want it written, and
  which should be argued on a survey of the existing types.
. Follow-on: carrying in-toto predicate types in other envelope and receipt
  families. The portability paragraph states the principle; what an evidence
  bundle looks like when the same predicate is carried in a different envelope,
  and how the index records it, is a separate document.
