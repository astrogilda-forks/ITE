[[abstract]]
== Abstract

The community meeting of 2026-08-07 agreed to give the predicate directory in
`in-toto/attestation` 2 tiers, `vetted` and `contrib`, and neither it nor ITE-9 settled what sorts a
submission into one. This ITE supplies that rule: to be listed as `vetted`, a type ships 3 items
of evidence in a signed bundle, through any of 3 paths, checkable by a maintainer who knows
nothing about the predicate's subject. Who gets published does not change, since today's bar still lands in
`contrib`.

[[specification]]
== Specification

=== Scope

This ITE changes:: The directory gains 2 tiers, a rule for which tier a type lands in, a
machine-readable index and defined transitions between them.

This ITE does not change:: The ITE-9 format, namespace assignment, who may publish, or any
listed type's status.

[[determinate]]
=== Determinate

[NOTE]
====
A predicate specification is *determinate* when 2 competent readers, implementing from the
specification text alone and without consulting each other, reach the same accept-or-reject
decision on the same input document.
====

Determinacy is not quality, completeness or scope: a useful specification is indeterminate if 2
readers disagree over whether a field is required. A non-expert can measure it, because
disagreement is observable without knowing who is right.

=== The tiers

The directory is a registry, and RFC 8126 supplies the vocabulary: `contrib` is _Specification
Required_, and `vetted` is _Expert Review_ against a criterion published in advance, not held in
a reviewer's head.

`contrib`:: Hosted and listed. Admission requires what it requires today, an ITE-9
specification and a maintainer check, plus an index record. In ITE-9's words, these are "not
mandated or endorsed".


`vetted`:: Determinate and independently implemented. Admission requires everything `contrib`
requires, plus the criterion below through 1 of the 3 paths, and any scope the project adopts.

The names are a mechanical substitution; use whichever pair the ITE Editors prefer. Tier controls
neither bindings nor namespaces.

[[criterion]]
=== Acceptance and promotion criterion

To be placed in `vetted`, a type MUST ship these 3 items as 1 signed bundle:

[cols="1,6"]
|===
| E1 | A conformance corpus with negative controls
| E2 | An implementation built from the specification text by someone other than its author

| E3 | Run results from each implementation, at least 1 taken blind
|===

[[signing]]
==== Who signs, and with what

The bundle is signed by whoever produced the runs in it, not by the project; where 2
implementers contribute runs, each signs their own. Each signature is a DSSE envelope over an
in-toto Statement over the corpus digest and the specification commit, so a
submitter needs nothing this repository does not ship. Key distribution is out of scope.

[[e1]]
==== E1, a conformance corpus with negative controls

Complete Statements, each labelled `MUST-ACCEPT`, `MUST-REJECT` or `INDETERMINATE`. Every
`MUST-REJECT` vector cites the clause that rejects it and the layer at which rejection occurs,
and one rejected by schema validation alone does not count toward coverage. The runner counts
coverage over every required field, every constrained field and each non-default parsing rule.
The corpus is published and run green in CI.

[[e2]]
==== E2, an implementation by someone other than the author

A named person, not an organisation, who was not a contributor to the specification as of the
commit their first run was taken against, and who has consented publicly to being named.
Contributions after that commit MUST NOT disqualify them. A validator that reads a Statement
and decides suffices, and each implementation's language and tooling MUST be declared.



[[e3]]
==== E3, published runs with a defect record

Each implementation's run against the full corpus, carrying the specification commit and corpus
digest; a `blind` or `directed` label on every run; and a record of every place the 2
implementations initially disagreed and what resolved it. The corpus digest is published before
the second implementer's first run, and that implementation and its output are committed before
any corpus change.

[[delegated]]
==== Delegated schemas

Where a schema is wholly delegated to an external specification with its own conformance suite,
citing that suite as the index record's normative reference satisfies E1 and E2, and the
submission ships vectors for the binding layer only.

[[promotion]]
=== Promotion from `contrib` to `vetted`

. A commissioned second implementer, satisfying E1 through E3.
. Observed adoption. A `contrib` type in independent production use by unrelated parties MAY be
  promoted without a commissioned implementation, on evidence of published attestations or named
  adopters, and MUST still ship E1.
. An independently authored corpus, run against the author's own implementation, satisfying E1
  through E3 inversely.

Promotion is a pull request adding the bundle. Maintainers confirm CI is green, that the second
implementer or corpus author is named and consenting, and that the signature verifies, after a
14 day objection period.



[[lifecycle]]
=== Lifecycle of a predicate type

A type is in exactly 1 state at any time. State is a field of its index record, which also
carries the short name, the `predicateType` URI, the specification's location, the tier and the
change controller. Maintainers decide every transition and write a reason for a rejection; a
change controller initiates deprecation and re-promotion, which returns a type to whichever tier
its evidence supports. Demotion costs a label, not a listing.


`proposed`:: Open, not merged, not in the index. Duplication and active harm are the only 2
grounds for rejection; absence of evidence is never one.
`contrib`:: Listed, not endorsed. Where every submission lands.
`vetted`:: Listed, criterion checked.
`deprecated`:: Listed, marked, resolvable. Superseded, abandoned or no longer passing.
`withdrawn`:: A tombstone, still listed because the URI may already be in published
attestations. Never deleted.
`observed`:: A registry entry only, in use elsewhere, not hosted here.

....
                     duplicate or harmful
  observed --> proposed --> rejected
                  |
                  | ITE-9 format
                  v      bundle + objection period
              `contrib` --> `vetted`
                  |  <--     |
                  |   corpus unrepaired
                  +--> deprecated <--+
                          |     |   superseded or abandoned
      maintenance resumes |     |   actively harmful
                          v     v
           `contrib` or `vetted`   withdrawn
....

[[motivation]]
== Motivation

The current process asks a reviewer to read a specification and judge whether it is good, which
scales worst with volume and needs the domain expertise to judge whether a type models its
subject. The
meeting recorded the cost: "Kubernetes about to start verifying attestations and just realized
they weren't being correctly produced", found by the consumer after publication.

[[reasoning]]
== Reasoning

Evidence has a property a judgement does not: the submitter can run it before submitting. The
shape is not novel, since RFC 2026 conditions advancement on "at least two independent and
interoperable implementations from different code bases". The criterion does not judge whether
a predicate is a good idea, its largest limitation. Applied on paper on 2026-08-08 to all 13
listed types and 8 open submissions, nothing satisfies E1, so this draft grandfathers.

[[backwards-compatibility]]
== Backwards Compatibility

ITE-9 describes the library as one that "provides peer-reviewed definitions of predicate
types". Under 2 tiers that describes `vetted`, not `contrib`, so this ITE amends it. Existing `vetted`
predicates MUST NOT be demoted on adoption, and no URI changes.

[[security]]
== Security

The first risk introduced is over-reading `vetted`, so the directory MUST state adjacent to
both listings that `vetted` means the specification is determinate and somebody other than its
author implemented it, and not that the predicate is a good idea or suits a given use.

The second is more serious. A tier makes `contrib` a place where a type that 2 implementers
would read into non-interoperating consumers can sit, listed, indefinitely, where today it
would be scrutinised into shape. 3 things bound that, none eliminating it: rejection for active
harm is unchanged, `withdrawn` answers a type found harmful after listing, and the
machine-readable tier lets a consumer refuse an unvetted type. A broken type nobody reports is
unmitigated.

[[infrastructure-requirements]]
== Infrastructure Requirements

Mostly existing machinery: a conformance corpus is a set of JSON Statements exercised by the
binding-test harness the repository already runs, and it may live in the submitter's own
repository pinned by digest, so hosting cost is unchanged.

Stated directly, the index is generated by a CI job, that job runs on merge, and the job does
not exist. This ITE asks the project to write it, as 1 generator and 1 workflow: the generator
emits the combined index from each type's record and reports divergence against
`layouts/index.redirects` in `in-toto/in-toto.io`, and the workflow runs it on merge, failing
the build on a difference. The drafter offers to write both.

[[prototype-implementation]]
== Prototype Implementation

None of that tooling is written. A corpus in the E1 shape is published at
link:https://github.com/probityai/agent-evidence-vectors[probityai/agent-evidence-vectors],
461 vectors across 8 corpora at tag v0.10.1, where a second
author's verifier, in another language, disagreed with the first over a maximum JSON nesting
depth the specification had not stated: between those depths the same bytes were valid to 1
conformant verifier and malformed to the other. The bound is now normative, where E3
asks it to be.
